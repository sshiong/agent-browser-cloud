# 远程桌面独立低分辨率视图闭环

> 日期：2026-09-23
> 状态：仓库级独立低分辨率 Viewer 完成；硬件 Codec 与目标 Linux 8 Client 长稳仍未完成
> 实现提交：`f47e2c7 feat: add independent remote desktop resolution`

## 问题

原有 `SMOOTH/BALANCED/SHARP` 只改变每连接 Tight JPEG 质量。noVNC 的 `scaleViewport` 也只是
客户端 CSS/Canvas 显示缩放，Gateway 仍传输 Chromium 原始 framebuffer 的全部像素。弱网 Viewer
即使选择流畅优先，仍需接收原始分辨率；直接调整 x11vnc 或 Chromium 分辨率又会同时影响 Agent、
其他协作者和结构化点击坐标。

## 修复

- `POST /sessions/{sessionId}:desktop-connection` 新增 25%—100% 的
  `resolutionScalePercent`，Control Plane 将其写入一次性 HMAC Ticket 和响应；越界值在 API 与
  Ticket 签发层双重拒绝；
- Browser Node 验签后按连接改写 RFB ServerInit 的宽高。旧 Control Plane 签发、不含新 Claim 的
  Ticket 默认 100%，保持 N/N−1 滚动兼容；
- 低分辨率连接收到 framebuffer 更新时，从共享 Hub 已合并的最新完整 Raw 基线生成独立完整画面，
  使用确定性最近邻采样降低像素数。共享上游、Hub 权威像素和其他 Viewer 不被修改；
- 低分辨率连接发来的 PointerEvent 按端点保持的比例映射回原始桌面并限制在有效边界，键盘、剪贴板
  及 Human Input Priority 语义不变；
- Bell/ServerCutText 等非 framebuffer 消息保持原样；低分辨率和 Tight JPEG 可叠加，先降采样再按
  该 Viewer 协商的质量编码；
- Web/Tauri 共享页面默认 75%，提供 50% 弱网、75% 推荐和 100% 原始选项。改变比例会只重连当前
  Viewer，因为 RFB framebuffer 尺寸在 ServerInit 阶段固定；页面明确说明不会改变 Chromium、
  Agent 或输入坐标；
- OpenAPI 仍保持 253 Operations / 350 Schemas，TypeScript、Python、Go、Java SDK 与 Manifest
  全部重新生成。

## 验证

真实 loopback TCP + WebSocket + RFB 3.8 用例完成完整握手：

1. 上游 VNC 声明并发送 4×4 Raw framebuffer；
2. 使用签名绑定 50% 比例的协作 Ticket 连接 Gateway；
3. 下游 ServerInit 与 framebuffer 均只暴露 2×2，像素负载由 64 字节降至 16 字节；
4. 下游向右下角 `(1,1)` 发送 PointerEvent；
5. 上游实际收到 `(3,3)`，证明输入仍命中原始 Chromium 右下角。

## 剩余边界

该改动关闭仓库内“独立低分辨率视图”代码缺口，但不冒充下列目标环境能力：

1. VideoToolbox、VA-API、NVENC 等硬件 Codec 与 GPU Helper；
2. 目标 Linux 上 8 个真实 noVNC 协作者的小时级弱网、抖动、丢包、重连与资源长稳矩阵；
3. 跨 Region Remote Desktop Relay、TURN/边缘接入和端到端网络 SLA；
4. 当前最近邻缩放偏向确定性、低成本传输；更高质量缩放器需在目标 CPU/GPU 预算下单独验收。
