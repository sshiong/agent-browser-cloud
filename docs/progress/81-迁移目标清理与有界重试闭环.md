# 迁移目标清理与有界重试闭环

> 日期：2026-07-30
> 状态：仓库级真实故障闭环完成；目标 Linux/Kubernetes 长稳和网络分区矩阵仍是生产 Gate

## 本轮关闭的问题

跨 Node 迁移原先只有成功路径。目标 `START_RUNTIME` 失败或超时后，Session 会进入
`FAILED`，迁移被直接标记失败；系统既不会先确认目标 Runtime 已停止，也不会排除失败
节点后重试。源端 `HIBERNATE` 超时时还可能长期停在 `HIBERNATING`。

这会产生两个生产风险：

1. 未确认旧目标停止就选择新目标，可能形成两个 Browser；
2. 一次目标节点局部故障会终止整个迁移，无法使用其他健康节点恢复。

## 已完成

### 持久化状态与滚动升级

- V056 对 `session_migrations` 进行 expand-only 扩展，新增：
  `target_attempt`、`maximum_target_attempts`、`failed_target_node_ids`、
  `target_cleanup_operation_id` 和 `last_target_failure_reason`。
- 新字段均有 N−1 安全默认值；JSON 和尝试次数约束使用
  `NOT VALID → VALIDATE`，没有删除或重命名列。
- 迁移阶段新增 `TARGET_CLEANUP`，`PLACING_TARGET` 和 `TARGET_CLEANUP` 都进入持久
  Scheduler 对账集合，Control Plane 重启后可以继续。
- N−1 Gate 固定 V056 的默认值、约束验证顺序和阶段兼容要求。

### fail-closed 清理与有界重试

真实状态机现在为：

```text
RESTORING 失败/超时
→ Session FAILED
→ MIGRATION_CLEANUP Operation
→ StopRuntime（Node Operation/Context Epoch fencing）
→ RuntimeStopped
→ Session HIBERNATED
→ 持久化失败目标
→ PLACING_TARGET（排除源和全部失败目标）
→ 第二次 RESTORING
```

- 只有 Node 返回匹配当前 Cleanup Operation 的 `RuntimeStopped`，迁移才允许重新
  Placement；清理超时会 fail-closed，不会冒险启动第二个 Browser。
- `StopRuntime` 对“目标尚未真正启动”保持幂等，因此启动前失败和部分启动都走同一
  清理屏障。
- 默认最多尝试 3 个目标。达到上限后迁移进入 `FAILED`，Session 保持
  `HIBERNATED`、Agent 不恢复，等待人工处理。
- 源端 Hibernation 或目标清理 Operation 超时会把 Session 收敛到 `FAILED`，不再永久
  卡在 `HIBERNATING`。
- Capacity Placement 接受失败节点集合，并继续强制
  `startRuntimeGenerationFloor=v1` 能力准入。

### API 与 UI 可观测性

Session Migration 正式 API 新增：

- 当前目标尝试数与最大尝试数；
- 已清理并排除的目标节点；
- Cleanup Operation ID；
- 最近一次目标失败原因；
- `TARGET_CLEANUP` 阶段。

Session Detail 的 Migration 卡片展示这些字段，不用颜色单独表达状态，也不在前端
模拟重试或资源变化。

## 真实故障验收

`tests/integration/smoke.sh` 将原双节点成功路径扩展为三个独立 Browser Node、三套
Storage Helper/Runtime/Profile Root 和共享 MinIO：

1. 源 Node 正常完成真实 Checkpoint；
2. 两个目标的 Storage Helper 在迁移前被终止；
3. 第一个目标 Restore 通过真实 `START_RUNTIME` Workflow 失败并超时；
4. 第三个 Node 的 Storage Helper 恢复；
5. 旧目标收到 fenced `StopRuntime` 并返回 `RuntimeStopped`；
6. 迁移持久化首个失败节点，第二次 Placement 只能选择第三 Node；
7. Checkpoint Restore、State Resync 和 Business Recovery 最终进入 `READY`。

最终断言 `targetAttempt=2`、失败节点列表精确包含首个目标、Cleanup Operation 存在、
源/失败目标/最终目标互不混淆，且最终只有权威 Placement 上的 Browser 为
`RUNNING`。完整 Integration Smoke 通过。

单元测试另覆盖：

- Hibernation timeout fail-closed；
- Cleanup Operation 创建与 `RuntimeStopped` 提交屏障；
- Restore 失败只派发持久 Cleanup；
- Cleanup 完成后才进入 `PLACING_TARGET`；
- 三次目标失败后有界终止；
- Placement 同时排除源节点和历史失败目标；
- N−1 Node 仍不能成为迁移目标。

## 回滚与运维

- V056 是扩展式迁移，不提供删除列的即时 Down Migration。
- 若需回滚到 N−1 Control Plane，应先暂停 Session Migration Scheduler，等待
  `TARGET_CLEANUP`/`PLACING_TARGET` 行收敛或由新版本完成；N−1 不会理解这两个进行中
  阶段，但新列默认值不会阻断其写入。
- 数据库列和新阶段约束在应用回滚期间保留。只有确认没有新版本实例、没有新阶段行且
  完成数据保留评审后，才可在独立 contract 版本删除。
- Cleanup 超时后的 Placement 预留会保守保留，避免误判 Runtime 已停止；值班人员必须
  先核对 Node Runtime/Operation Epoch，再执行手工释放。
