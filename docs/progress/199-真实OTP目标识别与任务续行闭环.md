# 真实 OTP 目标识别与任务续行闭环

> 日期：2026-09-21
> 状态：仓库自有受控 OTP Fixture 与真实 Chrome Gate 已完成；真实短信、邮箱、TOTP、企业 IdP 和客户站点仍属于目标环境 Gate。

## 问题

此前一次性 `OTP` Secret、人工响应 Intent 和任务续行代码虽已存在，但缺少端到端真实浏览器证据。
新增 Gate 首次运行证明真实 OTP 输入框无法绑定：Browser State 为避免泄漏会清空敏感控件的
`name/value`，而 Challenge 检测仍依赖 `name` 中出现 OTP 关键词。随后目标绑定又暴露旧数据库约束
只允许无 Target 的 OTP 事件；同一轮真实运行还发现 Node 重投相同资源采样会触发唯一键冲突并重复
进入危险事件处理路径。

## 实现

- Browser Node 仅在敏感输入包含标准 `autocomplete=one-time-code` token 时投影隐私安全的
  `controlType=one-time-code`；敏感控件的名称和值仍为空，不投影 OTP 正文或低熵 Hash。
- Challenge 检测使用该受限控件类别识别可见、启用的 textbox/combobox，并保留精确 Target、
  Element ID、Bounds 和 Visual Anchor 围栏。
- V126 以 `NOT VALID → VALIDATE → 切换约束` 的滚动升级方式同时接受 N−1 的无 Target OTP 事件和
  新版本的 Target-bound OTP 事件；其他 Challenge 类型的约束不放宽。
- 资源采样在 Session Placement 行锁内按 `(session_id, observed_at)` 幂等，重复投递不再重复写入，
  也不会再次触发 OOM 等危险保护副作用。
- 真实登录矩阵新增第四个独立 Profile：真实 Chrome 打开受控 OTP 页面，原 Task 进入
  `WAITING_FOR_HUMAN`，操作员 API 提交用途绑定的一次性 OTP Secret，原 Task 恢复并由独立
  Outcome Verifier 确认最终标题和状态。Fixture 日志只记录成功布尔值，不记录 OTP。
- Gate 额外拒绝 Control Plane 日志中出现资源采样唯一键冲突或 Challenge Target 约束失败，避免
  只看最终页面而遗漏后台重放错误。

## 验证

- `ChallengeDetectionServiceTest`、`SessionResourceDangerProtectionTest`：通过；覆盖敏感名称为空时
  的标准 OTP 类别识别，以及重复 OOM Sample 不重写、不重放保护动作。
- `cargo test --locked --manifest-path apps/browser-node/Cargo.toml -p state-collector`：35 通过，2 个
  需显式真实浏览器环境的测试按设计忽略。
- `make test-upgrade-compatibility`：通过，V126 N/N−1 兼容证据已进入 Gate。
- OrbStack + Google Chrome 153 `make test-real-login-agent`：通过。四个独立 Session/Profile 完成
  登录成功、错误密码、假成功拒绝和 OTP 续行；13 次 fixture 模型请求，OTP Task 为
  `COMPLETED/VERIFIED`，`secretValuesPrinted=false`。
- OrbStack `make test-integration`：通过，完整 PostgreSQL/Redis/MinIO/mTLS/Chromium、Agent、
  Challenge、Profile、恢复和双 Coordinator 链未回归。
- `make ci`：通过，包含 Java、Rust、Web 143 项、Worker、契约、四语言 SDK 和文档检查。

## 保留边界

该 Gate 证明产品代码能在真实 Chrome 中识别标准 OTP 控件、等待真人提供代码、一次性代填并恢复
原任务；它没有连接真实短信/邮箱/TOTP Provider，也没有绕过第三方 IdP、跨域 iframe 或支付确认。
这些场景需要客户授权 Fixture、真实凭据、站点契约、风险策略和目标环境验收，不能由仓库 Fixture
结果替代。
