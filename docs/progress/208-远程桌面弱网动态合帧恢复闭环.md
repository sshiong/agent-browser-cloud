# 远程桌面弱网动态合帧恢复闭环

> 日期：2026-09-23
> 状态：仓库级弱网 Viewer 积压恢复完成；独立低分辨率视图随后由 progress 209 关闭；硬件 Codec 与目标 Linux 8 Client 长稳仍未完成
> 实现提交：`d22987d fix: keep weak remote desktop viewers connected`

## 问题

Remote Desktop Gateway 已有单上游 RFB Fan-out、每 Actor 带宽/FPS 配额和容量为 4 的有界广播
队列。旧逻辑在某个 Viewer 因带宽配额等待而落后队列时返回 `Lagged`，随后直接关闭这个 Viewer。
这能保护其他协作者，但把正常的弱网背压误当成终止条件：快 Viewer 可继续，慢 Viewer 必须重连。

更隐蔽的风险是，若只在 `Lagged` 后补发最新完整画面而不重置订阅游标，广播队列中仍保留的旧增量
会在完整画面之后继续发送，形成视觉倒放。

## 修复

- Hub 继续维护每次上游更新后的精确完整 Raw framebuffer，不改变 Chromium 分辨率、共享上游或
  坐标空间；
- Viewer 发生 `Lagged(n)` 时先重新订阅广播，再读取最新完整基线。重订阅发生在读取基线之前，
  因此陈旧增量不会重放，读取期间出现的新更新也不会遗漏；
- 跳过的帧计入已有单调 `throttled_batches`，不把弱网压力隐藏成零成本成功；旧 Control Plane/
  Proto/数据库无需新增字段，N/N−1 语义保持兼容；
- 只有显式协商 lossy Tight JPEG 的 Viewer 会按积压临时把恢复基线限制为质量 30，积压达到队列
  容量时限制为质量 20；后续实时帧立即恢复客户端原协商质量；
- Raw-only 与 noVNC Quality 9 连接保持无损，不会被服务端擅自切换为 JPEG；
- 人类输入仍走独立、250 ms 有界的上游输入队列，不等待 Observer 图像带宽/FPS 配额。

## 验证

新增真实 loopback TCP + WebSocket + RFB 3.8 回归：

1. 建立一个 250 Kbps、60 FPS 上限的只读 Viewer；
2. 在首帧仍受配额等待时向共享 Hub 连续写入超过队列容量的完整帧；
3. 验证 Viewer 先收到已经在途的像素值 `10`，随后直接恢复最新完整基线 `16`；
4. 再写入新帧 `17`，验证同一连接继续收到 `17`，没有回放 `11—15`；
5. 验证连接仍在线，且 throttled 计量包含配额等待与被合并帧。

已通过：

- 定向真实弱网用例单独通过，执行时间约 1.6 秒；
- `cargo test --workspace`：通过，只有原有的外部 Chromium/S3 条件用例按设计忽略；
- `cargo clippy --workspace --all-targets -- -D warnings`：通过；

## 剩余边界

该改动关闭“单 Viewer 因正常弱网积压被直接踢下线”的仓库代码缺口，但不冒充下列目标已完成：

1. VideoToolbox/VA-API/NVENC 等硬件编码链与 GPU Helper；
2. 目标 Linux 上 8 个真实 noVNC 协作者的小时级弱网、抖动、丢包、重连与资源长稳矩阵；
3. 跨 Region Remote Desktop Relay、TURN/边缘接入和端到端网络 SLA。

独立低分辨率 Observer 视图已由
[progress 209](209-远程桌面独立低分辨率视图闭环.md)以逐连接服务端降采样和输入坐标映射关闭。
