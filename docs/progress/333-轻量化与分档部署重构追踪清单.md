## Phase 0 架构盘点结论

| 能力域 | 改造前现状 | 强依赖问题 | 重构落地路径 |
| --- | --- | --- | --- |
| Browser Runtime | Rust `runtime-supervisor` + `state-collector` + `input-sandbox` 已成熟 | 仅通过 `node-agent` gRPC 暴露，需 Control Plane 驱动 | 由 `crates/lite-server` 直接进程内复用，实现 L0 独立运行 |
| 外部 MCP 接入 | Python `apps/mcp-gateway`（16 工具），转发 Java Control Plane | L0 需额外部署 Python + Java + PG + Redis | L0 内置纯 Rust `/mcp`（收敛 10 工具）+ 纯 Rust STDIO Bridge |
| 托管模型 Worker | 4 个独立 Python 容器（Agent/Reviewer/Outcome/Vision） | 重复 Python 解释器/容器/内存开销 | 新增纯 Rust `crates/worker-supervisor` 单进程多队列并发调度 |
| 镜像构建 | 单一全量镜像（含 Xvfb/x11vnc + OpenCV/Tesseract） | 无头场景白占 ~700MB 镜像与构建时间 | 拆分为 `lite` / `core` / `desktop` / `vision` 四阶段目标 |
| Profile 持久化 | L1/L2 支持 S3 Multipart；L0 初始为整包 `tar.zst` | 每次 Checkpoint 重写全部未变文件 | 升级为文件级内容寻址 Chunk（`chunks/<sha256>.zst`）去重 |
| 背压与调度 | Control Plane 已有自动扩缩与 PSI，瞬时毛刺易触发高压力拒绝 | 缺少 EWMA/P95 分级平滑与 I/O 综合评分 | Rust 侧引入六态 EWMA/P95 分级背压，L2 调度纳入 I/O 综合评分 |

## 实测指标记录（OrbStack + 真实 Chromium 156 + 非 root 沙箱/seccomp 实机验收）

> 实测环境：macOS OrbStack (`OS=OrbStack Server=29.8.2`, ARM64 Linux 容器)，限制 `--memory=2g --cpus=2.0 --shm-size=256m --security-opt seccomp=./deploy/docker/chromium-seccomp.json`（保留完整非 root Chromium 沙箱，无 `--no-sandbox`，不裸露 CDP 端口），`BROWSER_LOW_MEMORY_MODE=true`。
> 压测工具：`apps/browser-node/target/debug/browsercloud-bench`（纯 Rust，对运行中容器发起真实 MCP Streamable HTTP + REST 请求并驱动真实 Chromium 156 页面操作）。

| 指标项 | 实测结果 | 说明 |
| --- | --- | --- |
| `browsercloud-lite` 镜像体积（L0 单容器） | **1.16 GB** | Debian Bookworm Slim + Chromium 156 + `chromium-sandbox` + 纯 Rust `browsercloud-lite`，零 Java/PG/Redis/Python/VNC/OpenCV/Tesseract |
| `browsercloud-worker-supervisor` 镜像体积 | **161 MB** | 纯 Rust 单进程合并 Agent/Reviewer/Outcome/Vision 四角色 Worker，替代 4 个 Python 容器 |
| L0 空载内存（0 会话） | **1.94 MiB RSS**（cgroup `current=7.45 MiB`, `peak=10.47 MiB`, CPU `0.00%`） | 包含 SQLite WAL、多 Agent 鉴权、AES-GCM Vault、SSE 事件总线、`/metrics` 与原生 10 工具 MCP |
| L0 2 并发真实 Chromium 156 会话峰值内存 | **339.5 MiB RSS**（cgroup `current=398.8 MiB`, `peak=402.8 MiB`, CPU `2.15%`） | Agent A + Agent B 同时运行 2 个独立进程隔离浏览器实例，折合单会话 ~170 MiB RSS |
| 会话全关闭后回收内存 | **5.77 MiB RSS**（cgroup `current=72.0 MiB`, CPU `0.00%`） | 浏览器进程彻底回收，无残留泄露 |
| 真实 Chromium 156 冷启动耗时（`browser_create`） | **311 ms**（Session A）/ **699 ms**（并发 Session B + 导航） | `runtime-supervisor` 无头模式（`display=""`） |
| 导航与观察耗时 | `navigate` **411 ms** / `observe(tree)` **17 ms** / `observe(diff)` **12 ms** | 均通过 MCP Streamable HTTP 端到端计测 |
| 交互操作与批处理耗时 | 单次 `click` **97 ms** / 4 步 `act_batch` **166 ms** / `wait(app_condition)` **10 ms** | 4 步批处理包含文本输入、**AES-GCM Credential Vault `value_ref` 密码注入**、原生 `<select>` 下拉选择与表单提交，折合 ~41 ms/步 |
| 休眠与自动唤醒耗时 | `hibernate` **72 ms** / `autoWake` **367 ms** | 关闭 Chromium 后保留 Profile，下次 `observe` 自动拉起并恢复状态 |
| 多 Agent 隔离与凭证库验收 | **PASS**（2 独立 Token 跨 Agent `browser_close` 拒绝；`value_ref` 仅内存解密且响应零明文） | 同步验证 Prometheus `/metrics` 与 `X-Trace-Id` |
| DOM `diff` vs `tree` 传输量对比 | 无变更/最小变更 `diff` **2,808 B vs 5,996 B（-53.2%）**；小页面点击全表刷新时 `diff` 封装 **7,596 B vs 5,996 B** | 大页面低变更率场景下增量收益显著，极小页面全量重排时建议结合阈值退回 `tree` |
| Profile v2 增量 Chunk 去重率（真实 Chromium Profile） | Save 1：1,198,723 B 原始（已排除缓存）→ **62,836 B**（69 chunks，压缩率 94.8%，336 ms）；Save 2：**154/173 chunks 复用（89.0% 复用率）**，仅新增 **19 chunks / 27,090 B**（432 ms） | 单元测试中未变更二次保存为 **100% 复用（0 新增字节）**；真实 Chromium 重启因 SQLite WAL/Pref 时间戳变更仍达 89% 复用 |

### 实机验收暴露并已修复的缺陷

1. **无头模式误传桌面 `display: ":99"`**：首次容器实测触发 `desktop runtime requires a VNC port`；已修复 `lite-server/src/runtime.rs` 中 `RuntimeSpec.display` 为空字符串（`""`），确保 `runtime-supervisor` 真正以无头模式启动 Chromium 156。
2. **临时资源清理**：实测完成后临时容器 `lite-bench-live` 与 `browsercloud-lite:bench` / `browsercloud-worker-supervisor:bench` 临时镜像均已清理。
3. **尚未纳入本轮实测的环境项**：72 小时连续长稳压测、20+ 复杂商业 SPA 站点并发极限测试与多机 L2 生产 K8s Gate 仍属于目标环境验收项，不在本轮估算替代。
