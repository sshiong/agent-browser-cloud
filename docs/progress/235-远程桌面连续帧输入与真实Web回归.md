# 远程桌面连续帧输入与真实 Web 回归

> 日期：2026-09-28
> 范围：Gateway 已绘制帧输入围栏、Web/noVNC E2E 运行路径。

完整 `make test-e2e` 暴露了 progress 233 的边界：假 RFB 上游持续以 30 FPS 返回完整帧时，Gateway 要求输入帧 ID 与**最新**上游帧 ID 完全相同。Viewer 已绘制画面仍可见，但在绘制与真人输入之间上游通常已产生下一帧，因此鼠标和按键被连续拒绝，真实 Web/noVNC 画面与输入回路失败。

Gateway 现在首先要求输入携带的 Frame ID 精确等于该连接已经绘制回执的 Frame ID；若上游后来产生新图像，允许已绘制帧与最新上游帧的单调采样时间相差最多 750 毫秒。超过界限的旧画面输入继续拒绝、释放已按下的键和鼠标并请求刷新。同一静止来源 Frame ID 不因墙钟时间流逝而失效。该容差用于持续更新的 RFB 画面，不能证明 750 毫秒内页面语义或坐标不变；高风险业务决定仍由独立 Intent/确认 Gate 控制。

本机 macOS 的 Gradle 缓存中 `protoc-gen-grpc-java` 为 x86_64 Mach-O，本机无 Rosetta，直接执行 `make test-e2e` 在构建 Control Plane 时失败。测试脚本支持显式 `E2E_CONTROL_PLANE_JAR` 指向已构建 Jar，默认路径仍执行本地构建；本轮用 OrbStack Linux ARM JDK 构建 Jar 后运行 Web E2E。E2E 的八个随机端口分配改为同时占用八个临时 socket 后统一释放，防止一次分配内部重复。

验证：Gateway 36 项单元/真实 RFB 测试和严格 Clippy 通过，包含连续短差距放行、旧帧拒绝、按键/鼠标释放；使用 OrbStack PostgreSQL/Redis、真实 Chromium、Node/Gateway、Control Plane 和 Web 的 `E2E_CONTROL_PLANE_JAR=... make test-e2e` 通过，输出 `real_web_console_e2e=true` 与 `viewer_rbac_e2e=true`。`E2E_CONTROL_PLANE_JAR` 只跳过本机 Gradle 构建，不跳过任何 E2E 步骤。提交 `b0f310a` 的 GitHub [CI](https://github.com/sshiong/agent-browser-cloud/actions/runs/36405395191) 与 [Desktop](https://github.com/sshiong/agent-browser-cloud/actions/runs/36405395170) 工作流均通过，包含完整 Integration 和 Windows/macOS 构建。

目标 Linux 八客户端小时级长稳、旧 Viewer 输入围栏覆盖、硬件编码及物理显示器实际呈现时间仍待独立 Gate。
