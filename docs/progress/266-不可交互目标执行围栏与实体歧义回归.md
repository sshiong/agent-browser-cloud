# 不可交互目标执行围栏与实体歧义回归

> 日期：2026-10-03
> 基线：`1b171f2346642d30cf0dbd6f77e6d3798d8a22c7`
> 范围：使已投影的不可交互标记在动作和文件执行路径真正生效。

## 发现与修复

公开 Commerce 的图片和标题投影为两个可见、同名 button；没有实体上下文时，现有
采集器将两者标为 `interactive=false`。但此前 Node `resolve_target` 只验证版本、
可见性、可用性和 Bounds，仍能返回这些目标；控制面动作授权和文件上传也没有检查
该标记。观察层拒绝并不等于执行层拒绝，这个缺口需要修复。

- 控制面单动作、Batch 的每个目标和拖拽终点必须可交互，失败发生在 Capability 验证、
  消费、动作尝试和 Node 派发之前。
- Node 解析 Target Ref 和稳定 Element ID 都检查当前权威目标的 `interactive`，
  普通动作和 Batch 共用该解析；没有根据位置选择一个歧义目标。
- 控制面文件上传在创建 Operation 前检查该标记，Node 在连接 CDP 前再次检查。
  隐藏但明确可交互的 `<input type=file>` 仍走原受治理上传路径。
- API、Protobuf、权限、敏感输入用途、Target Revision、文档身份和网络 Quiet 没有放宽。
